# НаРуки

## What This Is

PWA-приложение для расчёта и прогнозирования заработной платы «на руки» для сотрудников в РФ. Пользователь вводит оклад «грязными» (до вычета налогов) и график выплат (аванс + зарплата), а система автоматически считает НДФЛ по прогрессивной шкале и показывает сумму, которая придёт на руки к каждой дате выплаты. Приложение рассчитано на нескольких пользователей с облачной синхронизацией данных между устройствами.

## Core Value

Пользователь может заранее и точно спланировать бюджет, зная сумму и дату ближайшей выплаты зарплаты на руки.

## Requirements

### Validated

- ✓ Пользователь может зарегистрироваться и войти в аккаунт, данные синхронизируются между устройствами через облако — Phase 1
- ✓ Пользователь может указать оклад «грязными» и график выплат (аванс + зарплата, 2 раза в месяц) — Phase 1
- ✓ Система автоматически рассчитывает НДФЛ по прогрессивной шкале (13/15/18/20/22% по накопленному годовому доходу) и показывает сумму на руки для каждой выплаты — Phase 1
- ✓ Пользователь может изменить размер оклада; система хранит историю окладов во времени — Phase 1
- ✓ Главный экран показывает сумму и дату ближайшей выплаты — Phase 1
- ✓ Пользователь может добавить разовую премию или компенсацию к конкретной дате выплаты; сумма облагается налогом по той же прогрессивной шкале, что и обычный доход — Phase 2
- ✓ Пользователь может внести отпуск (даты); система автоматически рассчитывает отпускные исходя из среднего дневного заработка за предыдущие 12 месяцев, с явным дисклеймером об упрощённом расчёте — Phase 3
- ✓ Главный экран показывает годовую сводку в виде pie chart (грязными / налог / на руки за календарный год) — Phase 4
- ✓ Приложение устанавливается на домашний экран iPhone как PWA и запускается в standalone-режиме — Phase 4

### Active

No active MVP requirements.

### Out of Scope

- Налоговые вычеты (на детей, имущественные и т.п.) — отложено на v2, усложняет расчёт налоговой базы без изменения базовой модели
- Учёт нескольких работодателей/источников дохода одновременно — v1 ограничен одним окладом на пользователя
- Offline-режим — v1 всегда требует подключения к интернету; PWA-манифест нужен только для установки на экран, не для офлайн-работы
- Сверка с фактическими начислениями от работодателя (импорт расчётных листков и т.п.) — приложение прогнозирует будущие выплаты, а не сверяет их постфактум

## Context

- Целевая аудитория — сотрудники с трудовым договором в РФ, которым нужно заранее знать сумму зарплаты на руки для планирования личного бюджета
- Стандартная схема выплат в РФ — 2 раза в месяц (аванс + основная часть зарплаты)
- С 2025 года в РФ действует 5-ступенчатая прогрессивная шкала НДФЛ (13/15/18/20/22%), применяется к доходу нарастающим итогом с начала календарного года — расчёт зависит от накопленного дохода, а не только от суммы текущей выплаты
- Отпускные по ТК РФ считаются через средний дневной заработок за предыдущие 12 месяцев — требует истории окладов и выплат пользователя за этот период
- Продукт мультипользовательский с облачной синхронизацией — нужен бэкенд, база данных и аутентификация, а не только клиентское PWA-хранилище

## Constraints

- **Платформа**: PWA, устанавливаемое на домашний экран iPhone (Safari/iOS «Добавить на экран Домой») — веб-манифест, иконки, standalone display mode
- **Налоговое законодательство**: Расчёты должны соответствовать актуальной прогрессивной шкале НДФЛ РФ (действующей с 2025 года)
- **Данные**: Мультипользовательский доступ с облачной синхронизацией — нужен бэкенд и база данных, локального хранения недостаточно

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Облачная синхронизация с аккаунтами вместо локального хранения | Приложением будут пользоваться разные люди, данные должны быть доступны с разных устройств | ✓ Better Auth + Neon Postgres, сессия 30 дней; конкурентная запись с двух устройств решается через `ON CONFLICT DO UPDATE` + подписанное подтверждение замены (Phase 1) |
| Налоговые вычеты не учитываются в v1 | Снижает сложность MVP, вычеты можно добавить позже без изменения базовой модели расчёта | — Pending |
| Отпускные считаются автоматически по среднему заработку за 12 месяцев | Пользователю не нужно вручную выполнять сложный расчёт по ТК РФ | ✓ Реализовано; `calculateAverageDailyEarnings` — посегментное пропорционирование по реальным календарным дням при изменении оклада (отклонение от буквального псевдокода RESEARCH.md, зафиксировано и обосновано в 03-01-SUMMARY.md), деление на факт. число месяцев при стаже < 12 (Phase 3) |
| Бонусы делятся на «премия»/«компенсация» (D-V02, реверс решения Phase 2 «без категории») | Только «премия» учитывается в базе среднего заработка для отпускных по ст.139 ТК РФ; «компенсация» исключается | ✓ Реализовано; поле `type` обязательно на всех уровнях (repo/validation/action/формы), БД-дефолт `'premium'` для существующих строк (Phase 3) |
| Offline-режим не требуется в v1 | Упрощает архитектуру до обычного SPA + API; PWA-манифест нужен только для установки на экран | ✓ Реализовано: пустой precache, без offline-кэширования (Phase 4) |
| Один оклад на пользователя, может меняться со временем | Покрывает основной сценарий; несколько источников дохода — потенциальное расширение v2 | ✓ `salary_history` хранит эффективные-датированные записи, замена требует подтверждения показанного значения (Phase 1) |
| Замена оклада перезаписывает значение без журнала аудита (D-14) | Проще модели данных; риск компенсируется UI-подтверждением показанного значения перед перезаписью | ✓ Реализовано как compare-and-swap с HMAC-подписанным подтверждением, устраняющим гонки между устройствами (Phase 1) |
| График выплат — числа месяца (день аванса/зарплаты), без истории графика (D-01) | Покрывает стандартную схему 2 раза в месяц; смещение на выходные/праздники и клэмпинг по факту месяца рассчитываются динамически | ✓ Реализовано; РФ-праздники через `date-holidays`, ограничение: разовые государственные переносы после 2022 могут не учитываться (Phase 1) |
| Разовая премия/компенсация облагается через тот же кумулятивный механизм НДФЛ, что и оклад | Не нужна отдельная налоговая модель — премия просто увеличивает накопленный годовой доход на дату выплаты | ✓ Реализовано; `getCumulativeIncomeBeforeDate` суммирует premия+оклад до расчёта прогрессивной шкалы (Phase 2) |
| Формы редактирования (BonusRow) используют React Hook Form `values` (не `defaultValues`) + явный `reset()` на Cancel/success | `defaultValues` читается один раз при монтировании и не ресинкается с изменившимся пропом — приводило к тихой перезаписи актуальных данных устаревшими (CR-01); паттерн стоит переиспользовать в будущих формах редактирования уже смонтированных строк (например, отпускные в Phase 3) | ✓ Реализовано и закрыто независимым код-ревью в два прохода (реинкарнация бага в `onEdit`-успехе была поймана вторым ревью и тоже исправлена); покрыто рендер-тестами на jsdom + @testing-library/react (Phase 2); паттерн переиспользован для VacationRow в Phase 3 (собственный рендер-тест) |
| Никогда не показывать вычисленное ₽0 как подтверждённую сумму выплаты, если исходные данные (история оклада) отсутствуют — использовать явное состояние «не настроено» вместо заглушечного нуля | Ноль, посчитанный из пустой истории, выглядит как настоящий подтверждённый результат и вводит пользователя в заблуждение; обнаружено дважды независимо в Phase 3 (в прогнозе следующей выплаты и — отдельно — на странице списка отпусков, один и тот же паттерн не был перенесён между двумя местами при первом фиксе) | ✓ Реализовано в `forecastNextPayment` (`configured:false, missing:"salary"`) и на `/vacations` (`grossKopecks: null` вместо `formatKopecks(0)`); правило актуально для любого будущего экрана, отображающего денежные суммы, посчитанные из истории оклада/бонусов/отпусков (учесть в Phase 4 pie chart) (Phase 3) |
