## User-story outcome

**As a** salaried user, **I want to** receive a clear validation message when my gross-salary
entry cannot be persisted as a positive kopeck amount, **so that** a typo never turns the
salary setup flow into an unhandled application failure.

## Design decision: one gap plan, two vertical refinements

This plan depends on 01-08 because that executed plan deployed the database constraint which
exposed the application-layer mismatch. Task 1 is the tracer: it proves one submitted
sub-half-kopeck value travels through the real schema/action seam and returns a field error
without reaching persistence, then proves a forced persistence rejection is serialized the
same way. Task 2 closes the final browser-side seam without introducing a new test runtime.
Both tasks refine an already-shipped vertical slice; there is no schema, package, or route
foundation to build.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form → Server Action | FormData is attacker-controlled even when the page renders only for authenticated users; numeric coercion must enforce the database's real precision. |
| Server Action → repository/Postgres | A validated request can still fail at persistence; raw database errors and money values must not cross back to the client. |
| Server Action transport → Client Component | Network, deployment/action-ID, or future implementation failures can reject the client promise after the event handler has started. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-09-01 | Tampering | `salaryInputSchema.grossRubles` | high | mitigate | Enforce the exact stored-precision predicate `Math.round(v * 100) > 0`; boundary-table tests prove the open sub-half-kopeck interval is rejected before repository access. |
| T-01-09-02 | Information Disclosure | `saveSalaryAction` persistence catch | high | mitigate | Return only a fixed Russian grossRubles field error; the mocked rejection test asserts the fake DB message and submitted amount are absent and no logging is added. |
| T-01-09-03 | Denial of Service | `SalaryForm.submit` rejected Server Action promise | medium | mitigate | Catch async rejection in the event-handler path and update the already-rendered serverError state; AST test pins the try/catch wiring. |
| T-01-09-04 | Elevation of Privilege | `saveSalaryAction` ownership | high | mitigate | Preserve `requireUserId()` as the first action operation and keep user identity out of FormData; action tests mock this boundary without changing its production ordering. |
| T-01-09-05 | Repudiation | failed salary mutation and cache revalidation | medium | mitigate | Failure returns an explicit structured result and never runs the success-only revalidation path; tests assert zero revalidation calls on both validation and persistence failure. |
| T-01-09-SC | Tampering | npm supply chain | high | mitigate | Zero package changes; all tests use installed Vitest and TypeScript, gated by package-file diff checks. |

ASVS Level 1; blocking threshold `high`. Every high-severity threat is mitigated by a
specific implementation and automated assertion. No database detail or salary amount is
returned in an error.
</threat_model>

## Flagged assumptions from the spec-less fallback probe

- **Boundary/precision (resolved):** persisted salary uses integer kopecks and JavaScript
  `Math.round`; therefore the exact acceptance predicate is `Math.round(v * 100) > 0`.
  The tests pin values below and exactly at the half-kopeck threshold.
- **Idempotency (no new assumption):** the gap changes rejection and error serialization only.
  Successful replacement idempotency remains the atomic `onConflictDoUpdate` behavior proven
  by 01-07; neither task retries or duplicates a write.
- **Concurrency (no new assumption):** validation failure performs no write and persistence
  catch does not alter the repository's concurrency semantics. The live Promise.all coverage
  in 01-07 remains authoritative.
- **Identity-model delta:** none. The action continues to derive the sole user ID from the
  authenticated session; this plan does not generalize "second device" into a new identity or
  synchronization architecture.
