## Design decisions made in this plan (not pre-resolved by CONTEXT.md)

- **Overlap is inclusive-boundary.** D-V11 says an overlap is "rejected at save time" without spelling out
  whether two ranges that only touch at a shared boundary day (e.g. `08-01..08-10` and `08-10..08-20`)
  count. This plan treats a shared boundary day as an overlap (standard inclusive range-overlap semantics:
  `existing.startDate <= newEndDate AND existing.endDate >= newStartDate`) — a single calendar day cannot
  be part of two different vacations at once, matching the plain-language reading of "отпуск может быть
  только один в один период" already drafted into 03-RESEARCH.md's own example error copy.
- **`deleteVacationIfFuture` cannot be a single atomic SQL statement.** `deleteBonusIfFuture` (Phase 2)
  expresses its date guard directly in a `WHERE gt(bonuses.date, today)` clause because a bonus's own
  `date` column IS its eligibility date. A vacation's eligibility date is `resolveVacationPaymentDate(startDate)`
  — a pure-function transform SQL cannot express — so this task's guard is necessarily read-then-write: a
  `SELECT` (scoped to `id`+`userId`) to fetch `startDate` and compute the payment date, then a conditional
  `DELETE` (also scoped to `id`+`userId`) only if eligible. The narrow race window between the two
  statements is accepted and documented in the threat model below, not solved — solving it would require
  persisting a payment-date column, which "MUST NOT persist a vacation's computed отпускные amount as a
  stored column" (this plan's own prohibition) argues against for the entitlement amount, but a payment
  DATE is not the entitlement amount itself; still, adding a persisted derived date column purely to make
  one guard atomic is out of scope for this phase and is not required by any locked decision.
- **`getCumulativeIncomeBeforeDate`'s vacation-gross computation always uses the vacation's OWN 12-month
  lookback**, recomputed fresh on every call from the full `salaryHistory`/`bonusRows` already fetched in
  that function — never a stored amount. This directly implements "MUST NOT persist a vacation's computed
  отпускные amount as a stored column" above, and keeps a single source of truth: if a user later corrects
  a backdated salary or edits a premium bonus inside some vacation's lookback window, every later payment's
  cumulative-before figure updates automatically on the very next read, with no cache to invalidate — the
  same guarantee D-10 already established for salary/YTD edits.
