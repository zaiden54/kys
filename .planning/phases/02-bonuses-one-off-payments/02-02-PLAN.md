<objective>
A saved bonus can be fully edited — amount and/or date — at any time including bonuses dated in the
past, with the change recomputing cumulative income and re-taxing every later payment forward
(D-B04). A bonus dated on or before today cannot be deleted; a future-dated bonus can be (D-B06). The
`/bonuses` history list becomes the full UI-SPEC-compliant surface: empty-state card, per-row
Edit/Delete controls with their own loading/error states, and a delete confirmation step.

Purpose: this plan is the expansion wave on top of Plan 02-01's tracer. It closes the two remaining
locked decisions the tracer deliberately deferred (D-B04 edit, D-B06 delete-guard) and finishes the
UI-SPEC coverage for the list and edit/delete surfaces that Plan 02-01's minimal read-only list did
not attempt.

Output: `updateBonus`/`deleteBonusIfFuture` in the bonus repository; `saveBonusAction` extended for
edits plus a new `deleteBonusAction`; a per-row `BonusRow` client component; the finished `/bonuses`
page; and a nav link from the authenticated app shell.
</objective>

## Flagged assumptions

- **UI-SPEC's List "loading" and "error: load failed" states are not implemented as written.** UI-SPEC
  §"Bonus List / History" describes a client-fetched list with a skeleton/spinner and a retry button on
  fetch failure. This codebase's established pattern (`src/app/(app)/settings/salary/page.tsx`,
  Plan 02-01's own `bonuses/page.tsx`) renders the list server-side during the page's own render —
  there is no separate client fetch step to show a spinner for, and a genuine database read failure
  during a Server Component render surfaces through Next.js's own error boundary, not a custom retry
  UI. This is a deliberate architectural consistency choice, not a silent drop: both UI-SPEC rows are
  resolved as N/A against this app's server-rendered-list architecture rather than implemented as
  written. If a future milestone moves the list to client-side fetching, both states should be
  revisited.
- **List "overflow" (vertical scroll only, no pagination)** is implemented as UI-SPEC's own documented
  planner-assumption fallback: natural page scroll, no virtualization, no pagination — reasonable for a
  personal-finance app where a user's bonus count stays in the dozens at most.

|----------|-------------|

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-02-06 | Elevation of Privilege | `updateBonus`, `deleteBonusIfFuture` | high | mitigate | Both repository functions filter `and(eq(bonuses.id, bonusId), eq(bonuses.userId, userId))` in the same statement that performs the write; a bonus id belonging to a different user resolves to zero affected rows by construction, never a post-hoc authorization check that could be skipped. |
| T-02-07 | Tampering | Client-supplied `bonusId` in `deleteBonusAction`/`saveBonusAction`'s edit path | medium | mitigate | `deleteBonusAction` validates `bonusId` as a well-formed UUID via Zod before it reaches the repository; a malformed id fails validation and never reaches a `uuid`-typed database comparison. |
| T-02-08 | Repudiation | Deletion-guard bypass (a modified client calls `deleteBonusAction` directly for a past bonus, bypassing the UI's confirm dialog) | high | mitigate | `deleteBonusIfFuture`'s date guard (`gt(bonuses.date, todayIsoInMoscow())`) is enforced inside the single atomic `DELETE` statement itself on the server, not only in the browser's confirm dialog — a direct action call for a past-dated bonus is rejected server-side regardless of what the client sent. |
| T-02-09 | Tampering | Concurrent edit of the same bonus from two devices | low | accept | Last-write-wins on a single atomic `UPDATE` statement addressed by primary key.
