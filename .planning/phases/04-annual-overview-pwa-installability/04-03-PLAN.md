<objective>
Close UAT gap G-04-2 (severity: major): both `src/app/(auth)/login/page.tsx` and
`src/app/(auth)/register/page.tsx` call `router.push()` immediately after
`authClient.signIn.email()`/`signUp.email()` resolves, with no `router.refresh()`
(or other session-invalidating step) in between. The destination routes are
gated by `(app)/layout.tsx`'s server-side `getSessionUser()` + `redirect('/login')`
check. Next.js App Router's client-side soft navigation does not, by itself,
force a fully fresh server read reflecting the just-set session cookie, so the
navigation can re-resolve back through the same unauthenticated gate instead of
committing to the authenticated page — reading to the user as "nothing happens"
on submit. Root cause fully diagnosed in
`.planning/debug/auth-no-redirect-standalone.md`: this is a pre-existing defect
from the Phase 01-02 tracer commit (db14032), unmodified by Phase 04, and both
pages carry the identical anti-pattern independently — first surfaced by this
phase's standalone-PWA UAT click-through (Test 2 in 04-UAT.md), which also
blocked Test 3 (AnnualPieChart visual verification).

Purpose: Unblock the two outstanding UAT items in 04-UAT.md (Test 2 issue, Test
3 blocked_by Test 2) so a human can complete Phase 04's real-device UAT
sign-off, and close a dormant defect that has existed since Phase 1.
Output: Fixed `onSubmit` handlers in both auth pages; strengthened automated
regression coverage for both flows that actually asserts the `router.push`
destination and its ordering relative to `router.refresh()` — the specific
structural blind spot the diagnosis identified (existing render tests mock
`useRouter` entirely and never assert `push` was called; `scripts/verify-auth-flow.mjs`
drives raw HTTP and never exercises client navigation at all).
</objective>

    Per G-04-2's root cause (.planning/debug/auth-no-redirect-standalone.md): in
    login/page.tsx's onSubmit, after the existing `if (error) { setFormError(...); return; }`
    guard, add router.refresh() immediately before the existing router.push("/")
    call on the success path. Per Next.js's useRouter docs
    (node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-router.md):
    refresh() re-fetches Server Component data for the current route and clears
    its client cache, so calling it immediately before push() forces the
    destination's server-side session read ((app)/layout.tsx -> getSessionUser())
    to be fresh rather than resolved against stale pre-auth data. This is a
    two-line addition to the success path only — do not touch the error branch,
    the form fields, or the isStandalone re-login hint block.

    In login/page.render.test.tsx, replace the inline `useRouter: () => ({ push: vi.fn() })`
    mock factory with a `vi.hoisted()`-declared pair of module-level spies
    (name them pushMock and refreshMock) returned from useRouter as
    `{ push: pushMock, refresh: refreshMock }`, so test bodies can assert
    against the same instances the component calls (a plain inline `vi.fn()`
    inside the factory is a fresh, unreachable instance on every call — this is
    exactly why the existing tests never asserted push was called). Reset both
    spies in beforeEach alongside the existing mockMatchMedia/mockNavigatorStandalone
    calls. In each new test: render LoginPage, fill the email/password inputs
    via fireEvent.change with values satisfying loginSchema (a valid email
    string; any non-empty password), submit via fireEvent.submit on the
    surrounding form (or fireEvent.click the submit button), then await the
    assertions with waitFor from @testing-library/react since onSubmit is
    async. For the error-path test, call
    `vi.mocked(authClient.signIn.email).mockResolvedValueOnce({ error: { message: "..." } })`
    before submitting, then assert pushMock and refreshMock were never called.
    Leave the three existing re-login-hint tests functionally unchanged — only
    the router mock's shape changes under them.
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-04-03-01 | Elevation of Privilege | login/page.tsx & register/page.tsx onSubmit (client navigation timing) | low | accept | The router.refresh()/router.push() fix changes only client-side navigation UX timing — it never establishes, bypasses, or weakens authorization. (app)/layout.tsx's getSessionUser()+redirect() and session.ts's requireUserId() remain the sole server-side authorization boundary, evaluated fresh on every request regardless of how the client arrived there; even if this fix were entirely absent, a user could still reach a protected route via manual reload/navigation once the session cookie is set, since the cookie itself (confirmed via direct HTTP test in the debug session) was never the broken part. |
