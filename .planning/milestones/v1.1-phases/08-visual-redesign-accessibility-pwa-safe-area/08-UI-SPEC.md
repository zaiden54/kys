## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.6 |
| Label | 14px | 400 (regular) | 1.4 |
| Heading | 18px | 600 (semibold) | 1.3 |
| Display | 28px | 600 (semibold) | 1.2 |

Font declarations: Body/Label/Heading use the system sans stack. Display uses Georgia serif (fallback: system sans) — it appears exactly once per screen, on the next-payment hero amount only, to visually signal "this is the computed truth" against the otherwise quiet sans-serif UI.

A fifth, supplementary size exists outside the template's 4-role table for numeric/date microcopy — see "Supplementary: Caption / Tabular Numerals" below. It is not a fifth first-class role; it is a rendering rule applied to existing Body/Label text used for dates and amounts.

Exactly 2 weights are used app-wide: 400 (regular, body copy) and 600 (semibold, headings/display/emphasis). No third weight is introduced.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1a1a1a` (dark) / `#ffffff` (light) | Page background, primary surface |
| Secondary (30%) | `#242424` (dark) / `#f9fafb` (light) | Cards (next-payment hero, bonus/vacation list container), persistent nav header, install banner |
| Accent text (10%) | `#10b981` (dark) / `#047857` (light) | Next-payment hero amount text, "Удалить"/underline links styled as accent, success indicators — **not** button backgrounds |
| Accent button background | `#047857` (identical value both modes) | Primary submit/confirm button backgrounds ("Сохранить", "Подтвердить и заменить", "Войти"/"Зарегистрироваться") paired with white button text |
| Destructive | `#ef4444` (dark) / `#b91c1c` (light) | Delete action links ("Удалить бонус", "Удалить отпуск"), destructive-confirmation copy, form validation error text |

Accent reserved for: the next-payment hero amount (Display role text), primary form-submit/confirm buttons, and success/confirmation indicators only. Accent is explicitly NOT applied to: secondary/cancel buttons (use `text-primary` or a neutral border instead), nav links, list-row action links other than the primary submit, or decorative elements. Never all interactive elements — most controls stay neutral (text-primary or bordered) so accent stays legible as a signal.

**Contrast correction (08-REVIEW.md CR-01/CR-02):** the original single `#10b981`/`#ef4444` values (identical across both color schemes) failed WCAG AA in two places — white button text on `#10b981` background (2.54:1, needs 4.5:1) and `#10b981`/`#ef4444` used as text color against light-mode surfaces (2.43-3.76:1, needs 3:1 large-text / 4.5:1 normal-text respectively). The fix splits the single accent token into two: a dedicated `--color-accent-button` background shade (`#047857`, emerald-700, ~5.5:1 with white text, unchanged across modes) for buttons, and a light-mode-only darkened `--color-accent` (`#047857`) / `--color-destructive` (`#b91c1c`, red-700, ~6.5:1 on white) for text/link usage, while dark mode keeps the original values (`#10b981` on `#1a1a1a` = 6.86:1, `#ef4444` on `#1a1a1a` = 4.62:1, both already passing AA). All ratios computed with the standard WCAG relative-luminance formula.

Supporting neutrals (not part of the 60/30/10 split, needed to implement it faithfully):
- Text primary: `#f5f5f5` (dark) / `#171717` (light) — body/heading/label text, 18-20:1 contrast against Dominant
- Text secondary: `#9ca3af` (dark) / `#6b7280` (light) — captions, muted metadata (payment kind, "придёт на руки"), verified ≥4.5:1 contrast against Dominant/Secondary
- Tertiary surface: `#2d2d2d` (dark) / `#f3f4f6` (light) — hover states, dividers, borders, skeleton-loading fill

## Supplementary: Component Contract

> Prose sections below inform the plan/executor's implementation shape but are not part of the
> template's rigid tables above. No prior-phase UI-SPEC.md exists yet as a structural reference
> (Phase 8 is this project's first UI-contract phase) — this shape is original to this file.

### Dark Mode Strategy

System-preference-only, via Tailwind's media-based `dark:` variant (locked, 08-CONTEXT.md) — no manual toggle. **CSS variable polarity: dark is the base/default, light is the `@media (prefers-color-scheme: light)` override.** This is a deliberate departure from the more common light-base/dark-override convention, chosen because this app is dark-mode-first by design intent (the emerald-on-near-black hero number is the primary visual signature; light mode is the secondary/override case, not the default assumption). Document this polarity clearly in `globals.css` so a future contributor does not "fix" it back to the conventional direction.

`install-banner.tsx`'s existing `dark:bg-zinc-800` usage is the closest current precedent and should be migrated to the new CSS-variable-driven tokens rather than left on raw Tailwind zinc utilities, so the whole app draws from one source of truth.

### Hero Next-Payment Card (`next-payment-card.tsx`)

Secondary-surface background, 1px tertiary-surface border, 12px corner radius, `lg` (24px) padding, subtle shadow in dark mode only (light mode relies on the border for definition, no shadow). The forecast amount (`formatKopecks(forecast.netKopecks)`) renders in the Display role (28px/600/Georgia serif) in the accent emerald color — the only place accent touches a numeric amount. All other amounts in the same card (gross, tax, breakdown lines) stay text-primary/text-secondary at Body/Caption size — accent must not spread across the whole card.

### Confirmation Panel (Salary Overwrite, `pay-setup-forms.tsx`)

Existing inline panel restyled, not rebuilt (locked, 08-CONTEXT.md — UI-03 already functionally satisfied here). Old (existing) value rendered struck-through and in text-secondary color; new (submitted) value rendered in text-primary weight-600, emerald accent if the new value is an increase over the old, no color change if a decrease. Both values in the identical money-format/tabular-nums rendering. Confirm button ("Подтвердить и заменить") uses the accent-filled primary-button style; an implicit cancel (editing the form again) uses no button of its own — matches the existing component's structure.

### Loading Skeletons

Match the final layout's shape exactly (row count, card dimensions) — never a generic spinner, never a layout shift when real content replaces the skeleton. Rendered in tertiary-surface fill color with a subtle ~1s opacity pulse (loop). `prefers-reduced-motion: reduce` disables the pulse animation entirely (static tertiary fill instead) per the accessibility contract below.

### Form Fields

Primary-surface background, 1px tertiary-surface border, 8px corner radius. Focus state: 2px accent-color outline with a visible offset (not just a border-color change — must be perceivable for keyboard users per UI-07). Every input has a real `<label>` element associated via `htmlFor`/`id` (or, where an existing pattern already uses `aria-label` on an unlabeled control — e.g. `bonus-row.tsx`'s edit-mode type `<select>` — that aria-label satisfies the same accessible-name requirement and does not need to be converted to a visible label unless the redesign naturally adds one). Placeholder-only labeling is never sufficient on its own.

### Persistent Nav Header

Secondary-surface background, 56px height, 1px tertiary-surface bottom border. Contains the app name ("НаРуки") as a tappable link to `/` (home), present on every `(app)` screen per UI-04's one-tap-home requirement. `env(safe-area-inset-top)` applied as top padding on this header specifically (per 08-CONTEXT.md's "applied once at the shared `(app)` layout's header/footer level" decision) — never per-screen, never per-component elsewhere.

### Money & Numerals

Every money amount and every date rendered anywhere in the app uses `font-variant-numeric: tabular-nums` via one shared CSS utility class, applied consistently on top of `formatKopecks()`'s existing formatting (which stays the single source of truth for the money string itself — this phase changes presentation only, never the formatting logic). This is the concrete mechanism behind UI-02.

### Accessibility (UI-07)

WCAG 2.1 AA basics only, matching the requirement's own "basic requirements" scope — not a full audit:
- Contrast: all Text primary/Text secondary values against Dominant/Secondary surfaces verified ≥4.5:1 (body text) / ≥3:1 (large text ≥18px) per the Color section above
- Focus indicators: 2px accent-color outline + visible offset on every interactive element (links, buttons, form inputs) — no focus-trap or skip-link additions beyond this (locked, 08-CONTEXT.md — "no focus-trap/skip-link additions beyond what a small app needs")
- Every form input carries a `<label>` (or equivalent `aria-label` per the Form Fields note above)
- `prefers-reduced-motion: reduce` disables the skeleton-pulse animation

### Safe-Area / PWA (PWA-01, PWA-02)

`viewport-fit=cover` set once in the root layout's (`src/app/layout.tsx`) viewport metadata export. `env(safe-area-inset-top)`/`env(safe-area-inset-bottom)` applied once at the shared `(app)` layout level — top inset on the persistent nav header (above), bottom inset as padding on the outermost `(app)` layout wrapper so content never sits under the iPhone home indicator. Single source of truth; no other component applies its own safe-area padding.

### Supplementary: Caption / Tabular Numerals

Outside the template's 4-role Typography table, a Caption rendering rule applies to short numeric/date microcopy (payment-kind labels, list-row dates, breakdown line amounts): 12px / weight 400 / line-height 1.4, monospace font stack, always with `font-variant-numeric: tabular-nums`. This is not a fifth first-class typography role — it is the concrete rendering rule that implements the Money & Numerals contract above wherever Body/Label-sized text carries a number or date.
