<objective>
Harden the login/registration flow so it earns real trust: no credential ever leaves the POST body (SEC-01), the login form cannot be used to enumerate accounts (SEC-02), and the session cookie carries the correct security flags on the deployments users actually reach (SEC-03).

06-RESEARCH.md (HIGH confidence throughout) found Better Auth v1.7.2 is already secure-by-default on all three fronts — a single `INVALID_EMAIL_OR_PASSWORD` code for both login-failure cases, `httpOnly`/`secure`/`sameSite` cookie defaults, POST-body-only credentials. This phase is mostly proof, not construction. The one real gap is at the UI layer: `login/page.tsx` still passes Better Auth's raw `error.message` straight through to the screen, which is the exact enumeration vector Better Auth's server design otherwise avoids. The tracer task closes that gap first — it is the highest-confidence, lowest-risk fix in the phase and the one piece every other task's verification logically depends on being true. The remaining tasks build outward from it: an automated script that proves SEC-01/SEC-02/SEC-03 empirically against a running server (not just by reading Better Auth's source), and a live PR-preview check for the one thing that can only be proven over real HTTPS — the `Secure` flag and `__Secure-` cookie prefix.

Purpose: Close the last security gap between the shipped v1.0 MVP and a login flow real users can trust with their financial data, using the real pre-production PR-preview environment Phase 5 stood up.
Output: A hardcoded generic login error (SEC-02) proven by new render tests; a new `scripts/verify-auth-security.mjs` proving SEC-01/SEC-02/SEC-03 against a local dev server; and a live PR-preview confirmation of SEC-01/SEC-03's HTTPS-only guarantees, captured as a `<verify><human-check>` for end-of-phase UAT (per `workflow.human_verify_mode=end-of-phase`).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser → Better Auth API (`/api/auth/sign-in/email`, `/api/auth/sign-up/email`) | Untrusted email/password input crosses into server auth logic |
| Better Auth error payload → `login/page.tsx`'s rendered error text | Server error detail crosses into client-rendered UI — an enumeration leak if passed through verbatim |
| Server → session cookie (browser) | Session token crosses into client storage; cookie flags determine what the client and any script running in it can access |
| `scripts/verify-auth-security.mjs` → local dev server | An automated script crosses into live auth endpoints using a disposable test account |
| Human verifier → Vercel-SSO-protected PR-preview | An SSO-gated boundary; only an authenticated Vercel account holder can reach it — no automated script can cross this one |
