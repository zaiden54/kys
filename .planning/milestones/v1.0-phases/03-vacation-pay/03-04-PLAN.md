  plan set derives its full behavioral contract directly from 03-CONTEXT.md's twelve locked decisions
  (D-V01 through D-V12) and 03-RESEARCH.md's five researched pitfalls, which together are a substantially
  more complete and domain-authoritative specification for a Russian-labor-law calculation than a generic
  automated classifier could produce. This is recorded here as an explicit resolution, not a silent drop.
- **03-UI-SPEC.md's List "loading" and "error: load failed" states are not implemented as written**, for
  the identical architectural reason Phase 2's 02-02-PLAN.md already established for the bonus list:
  `/vacations` is a server component rendering `listVacations(userId)` during its own render, with no
  separate client-fetch step to show a spinner for or a retry button to attach to a failed fetch. A real
  database failure during that render surfaces through Next.js's own error boundary, not a custom retry
  UI. Both UI-SPEC rows are resolved as N/A against this app's server-rendered-list architecture, exactly
  as Phase 2 resolved the same two rows for `/bonuses` — not silently dropped, and revisit-worthy only if
  a future milestone moves either list to client-side fetching.
- **03-UI-SPEC.md's one genuinely unresolved consideration — mobile column alignment on the vacation list
  below 640px — is resolved by directly reusing `bonus-row.tsx`'s existing responsive grid pattern**
  (`grid-cols-[5.5rem_1fr] gap-x-3 gap-y-2 ... sm:grid-cols-[6rem_7rem_minmax(0,1fr)_auto] sm:items-center`):
  a stacked two-column grid below the `sm:` breakpoint, the full multi-column grid at `sm:` and above. This
  is the exact pattern already proven in this codebase for an analogous list, so it introduces no new
  responsive-design idiom.
- **The three-way `selectNextPaymentEvent` tie-break** (an exact date collision between a scheduled event,
  a bonus, and a vacation-derived date) is a planner discretion call, documented in `must_haves` above as
  a `backstop`-verified truth: candidates are built in the order schedule, bonus, vacation, and a stable
  sort by `dateIso` means the first-listed candidate wins an exact tie — schedule beats bonus (Phase 2's
  existing rule, unchanged) and both beat vacation.

## Design decisions made in this plan (not pre-resolved by CONTEXT.md)

- **A vacation-only resolved event never populates `NextPaymentForecast.breakdown`.** The existing
  `breakdown` field's shape (`{ salaryOrAvansKopecks, bonusKopecks }`) describes a combined
  salary/avans-plus-bonus payment on one date; a vacation's own gross is not a combination of those two
  components. A vacation landing on the exact same calendar date as a scheduled payment or bonus is
  possible but rare and is explicitly out of this plan's scope (per the tie-break rule above, the
  non-vacation event wins that slot anyway, so this combination can never actually reach the UI as a
  vacation-kind forecast) — no combined vacation+salary or vacation+bonus breakdown format is designed.
- **`getCumulativeIncomeBeforeDate` is called for a vacation-only event with `kind: "avans"`** (the lowest
  `PAYMENT_KIND_RANK`), exactly matching the existing bonus-only precedent in `forecastNextPayment` — safe
  for the same reason: by construction of the tie-break above, a vacation-only resolved event never shares
  its exact date with a scheduled event.
