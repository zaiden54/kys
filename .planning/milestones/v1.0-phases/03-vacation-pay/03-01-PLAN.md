## Design decisions made in this plan (not pre-resolved by CONTEXT.md)

- **The 12-month lookback window excludes the vacation's own start month.** 03-RESEARCH.md's "Otpusknye
  Calculation Engine" Pattern 1 pseudocode (`offset = 11 - i`, running `i` from 0 to 11) actually iterates
  the vacation's own start month as the *last* of its 12 "preceding" months — an off-by-one. 03-RESEARCH.md's
  own prose is unambiguous and matches `.planning/research/FEATURES.md`'s "Period" note: "the 12 calendar
  months **preceding** the month the vacation starts (not the 12 months preceding the request date)." This
  plan implements the corrected window: for a vacation starting in August, the 12 lookback months are
  August of the prior year through July of the current year — August itself is never included. This is a
  correction of a research artifact bug per the planner's standing authority to fix demonstrated sketch
  errors before implementation (matches the STATE.md Phase 1 precedent of correcting `01-PATTERNS.md`'s
  `nowInMoscow()` sketch before implementation).
- **Day-level proration uses the same 29.3 daily-rate divisor inside a month, not the month's actual
  calendar-day count.** 03-RESEARCH.md's Pattern 1 illustrative code prorates a mid-month raise as
  `daysAtRate x (monthlyRate / 29.3)` for each rate segment — i.e., 29.3 is reused as the average
  days-per-month divisor for intra-month day-weighting too, not `daysInMonth`. This plan adopts that
  approach as specified (MEDIUM confidence per 03-RESEARCH.md's own confidence breakdown for this specific
  sub-rule), since no stronger authority contradicts it and D-V04 only locks the *outcome* ("day-level
  proration"), not a specific formula.
- **Rounding happens exactly once, at the final `averageDailyKopecks` division.** No per-month or
  per-segment intermediate value is rounded — matches the "round once, at the end" discipline already
  established by `../tax/calculate-ndfl.ts`'s `roundToRuble`, avoiding 12x compounding rounding drift.
- **`resolveVacationPaymentDate` is a vacation-domain function that calls a schedule-domain export, not
  the reverse.** `shiftOffWeekendsAndHolidays` (generic calendar shifting) stays in
  `src/domain/schedule/resolve-payment-date.ts`; `resolveVacationPaymentDate` (the ст.136 ТК РФ "minus 3
  calendar days" business rule) lives in the new vacation module and imports the shift helper — matching
  this codebase's existing sibling-domain-module import discipline (e.g. `payment-accrual.ts` importing
  from `resolve-payment-date.ts`).
