<objective>
Reclassify bonuses with an explicit `type` ("premium" | "compensation") across the whole write path —
repository, validation, Server Action, and both bonus forms — so the vacation-pay engine (built in Plan
03-01, wired into the forecast in Plan 03-04) has a real, user-settable signal for which bonuses belong
in the отпускные average-earnings base (D-V02/D-V03).

Purpose: this plan reverses Phase 2's deliberate "no bonus category" decision (D-B07) on purpose, per
03-CONTEXT.md's explicit note that this reversal is intentional and user-confirmed, not a mistake to
simplify away. It must land before Plan 03-04's forecast integration, since that plan filters real bonus
rows by `type` when computing an upcoming vacation's gross pay.

Output: `createBonus`/`updateBonus` accept a `type` parameter; `bonusInputSchema` validates it
(defaulting to `"premium"`); `saveBonusAction` threads it through; both the create and edit bonus forms
let the user choose it, defaulting to `"premium"`.
</objective>

## Design decisions made in this plan (not pre-resolved by CONTEXT.md or UI-SPEC.md)

- **03-UI-SPEC.md does not cover the bonus-type selector at all** — it is scoped entirely to vacation UI.
  03-RESEARCH.md's Open Question #1 explicitly leaves the label/hint copy to "Phase 3 UI implementation."
  This plan resolves it: label "Тип выплаты", options "Премия (учитывается при расчёте отпускных)" (value
  `premium`) and "Компенсация — например, к отпуску (не учитывается при расчёте отпускных)" (value
  `compensation`), with the option text itself carrying the vacation-relevance explanation rather than a
  separate tooltip, keeping the form free of a new UI pattern this codebase doesn't otherwise use.
- **The bonus display row (non-editing mode) does not show the type.** Out of D-V02/D-V03's scope, which
  only requires the field to exist and be settable; adding a badge/filter to the history list is left
  alone to keep this plan's diff minimal and focused.
