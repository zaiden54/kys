## User-story outcome

**As a** user typing the date my salary changed, **I want to** be told plainly when the date I entered
does not exist, **so that** my pay history never silently records a different day than the one I meant
— and **as the person deploying this app**, I want the documented setup to refuse to start rather than
quietly run on a secret published in the repository.

## Design decision: two independent one-file fixes, each already wired end to end

Both surfaces here are already fully wired vertical slices; each has exactly one defective predicate
at its centre. The shared date validator is consumed by both Server Actions and, through the same Zod
resolver, by the browser forms, so tightening the single predicate closes the server path, the client
path and both dated inputs at once — no component, action, or route change is needed for the fix to be
end to end. The authentication secret is consumed by the environment parser at boot, so moving its rule
into an importable schema makes the boot gate directly testable without booting.

The two tasks share no files with each other beyond the validation directory and share none with plans
01-10 or 01-11, so this plan runs in parallel with 01-10 in wave 1.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form / direct Server Action POST → validation schema | Both dated fields are attacker-controlled strings; a value that passes here reaches a Postgres date column, so calendar validity must be decided at this boundary and not delegated to the database's own parser. |
| Repository / deployment environment → application boot | The environment file is supplied by whoever deploys; the boot parser is the only gate between a published placeholder and a live authentication secret. |
| Authentication secret → every derived credential | Session and confirmation-claim integrity are derived from this one value; its predictability is a total compromise of both. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-12-01 | Spoofing | Better Auth sessions under a published secret | critical | mitigate | The shipped template value fails validation at boot and the schema rejects placeholder markers and low-entropy values, so a verbatim copy of the documented setup cannot start. |
| T-01-12-02 | Tampering | HMAC-signed salary confirmation claims (plan 01-11) | high | mitigate | Claim integrity derives from the same secret; this plan is a declared dependency of 01-11 so the claim can never rest on a public value. |
| T-01-12-03 | Tampering | impossible dates reaching a Postgres date column | high | mitigate | The shared validator round-trips the parsed value against the submitted string, so behavior no longer depends on divergence between JavaScript and Postgres date parsing. |
| T-01-12-04 | Repudiation | a dated salary or baseline row recording a day the user never entered | high | mitigate | The submission fails visibly rather than persisting a normalised value; the table asserts every overflow class on both dated inputs. |
| T-01-12-05 | Information Disclosure | validation and boot error messages | medium | mitigate | Messages name the variable, the rule and the remedy only; a test serialises the error and asserts the candidate value is absent. |

## Flagged assumptions

- **No year-range rule.** Calendar validity is the whole scope. D-13 permits backdating and D-15
  permits a far-future effective date, so any plausible-year window would be a product decision this
  gap does not authorise. Recorded rather than silently added.
- **Placeholder detection is heuristic by design.** A denylist of exact strings would be defeated by
  the next template edit, so the rule matches distinctive markers instead. The residual false-positive
  risk is accepted at low severity in the threat register, because its failure mode is a loud boot
  refusal rather than a silent weak secret.
- **Operational break is intentional.** Any deployment currently running the shipped placeholder will
  refuse to start after this change. That is the fail-closed outcome AUTH-01 requires; the summary must
  record it so it is not mistaken for a regression.
- **Known-open WARNING, deliberately not planned here.** 01-REVIEW.md WR-03 (the authentication
  verification script's cleanup is bypassed on its assertion-failure path) is not in
  01-VERIFICATION.md's `gaps` block and stays out of scope for this gap-closure round. Recorded so it
  is not silently lost.
