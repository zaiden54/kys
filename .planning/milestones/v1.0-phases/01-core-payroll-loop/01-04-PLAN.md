## Test-database strategy (resolves 01-VALIDATION.md Wave 0 open item)

`01-VALIDATION.md` left "local Postgres vs. per-run Neon branch" unresolved. Decision for Phase 1: the integration suite runs against the same Neon database named by `DATABASE_URL`, isolating itself by creating throwaway `user` rows with random ids in `beforeEach` and deleting them in `afterEach` (cascade removes the dependent salary/schedule/baseline rows). This needs zero extra infrastructure, and cascade-delete isolation is verified by the suite's own per-user isolation test. Revisit if CI later needs parallel runs, at which point Neon branching is the documented upgrade path.

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 1: Confirm what "collides for that period" means for the backdated-overwrite rule (D-14)</name>
  <decision>Does a backdated salary entry overwrite an existing row only when the effective dates match exactly, or whenever the new entry falls inside the date range an existing row currently covers?</decision>
  <context>
    D-14 is the one decision in this phase rated one-way: the prior salary value is dropped at write time with no audit trail, so a wrong reading is not recoverable without adding an audit-log migration later. The overwrite behaviour itself is settled and is not being re-asked.

    What is genuinely unresolved is the granularity. `01-RESEARCH.md` Assumption A4 and Open Question 1 record that D-14 says "collides with an existing salary_history record for that period" without defining "period", and explicitly flags this for planner confirmation. Plan 01-01 already created a unique index on `(user_id, effective_from)`, which implements the exact-date reading — choosing range-overlap here means changing that constraint and the collision query before any real data exists.
  </context>
  <options>
    <option id="exact-date">
      <name>Exact effective-date match (RESEARCH default)</name>
      <pros>Predictable and explainable: "you already have an entry dated 1 March, saving another one dated 1 March replaces it." Matches the unique index already in the schema. Backdating a correction to a different day simply adds a second history row, so nothing is lost by surprise.</pros>
      <cons>Correcting a mis-typed salary that was recorded on a slightly different date leaves two rows, and the user has to notice and delete or re-date the stale one.</cons>
    </option>
    <option id="range-overlap">
      <name>Range-overlap match</name>
      <pros>A backdated correction anywhere inside a period sweeps away the row governing that period, so "fix the wrong number" is a single action with no leftover row.</pros>
      <cons>Destroys more than the user asked for: one backdated entry can silently delete a row dated weeks earlier, with no audit trail to recover it. Requires replacing the unique index with a range query and re-deriving period boundaries on every write.</cons>
    </option>
  </options>
  <resume-signal>Select: exact-date or range-overlap</resume-signal>
