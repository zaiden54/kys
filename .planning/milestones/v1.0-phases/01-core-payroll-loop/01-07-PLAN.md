## Design decision: why the fix belongs at the database layer, not in the action

01-PATTERNS.md § 2 makes this call explicitly and this plan adopts it: do **not** restructure
`saveSalaryAction`'s control flow, and do **not** add app-level locking.

The D-14 confirmation prompt genuinely needs `findSalaryAt` — the user must be shown the
existing amount before confirming an overwrite. That read is advisory by nature and can never
be made race-free by reading harder. What must be race-free is the *write*. Once the write is
a single `INSERT ... ON CONFLICT DO UPDATE`, Postgres itself serialises the two concurrent
submissions on the unique index: both callers succeed, exactly one row exists afterward, and
the second write updates rather than colliding. No update is lost invisibly and no
primary-key violation escapes to the user.

An advisory-lock or retry scheme would add a failure mode (lock leaks, retry storms across
the Neon HTTP driver's per-statement connections) in exchange for nothing the single statement
does not already give.

## Design decision: why a single statement works on the Neon HTTP driver

The existing doc comment on `replaceSalaryAt` correctly notes that `drizzle-orm/neon-http`
cannot run interactive transactions. That constraint does not block this fix and this is the
reason the fix is shaped this way: `INSERT ... ON CONFLICT DO UPDATE` is **one** SQL
statement, so it is atomic at the statement level without any transaction wrapper. The
driver's limitation is exactly why the multi-round-trip shape had to go, not a reason to keep it.

## Design decision: `created_at` is refreshed on conflict

`salary_history.created_at` records when a fact was recorded. Under the old delete-then-insert
the replacing row got a fresh `created_at`; under a plain conflict-update it would silently
inherit the replaced row's value. D-14 says the new entry *replaces* the old one with no audit
trail, so refreshing is both truer to the decision and behavior-preserving. The `set` clause
therefore refreshes it with a real UTC instant — never the Moscow wall-clock carrier introduced
by 01-06, which that plan's own threat model forbids from reaching any timestamp column.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| two authenticated devices → one user's rows | The same legitimate owner writes concurrently from two sessions. This is a supported product scenario (cross-device sync is a stated core constraint), not an attack — but it is the condition under which the current code loses data |
| Server Action → Postgres | A multi-round-trip write leaves the database observably half-applied between statements, with no rollback available |
| Neon HTTP driver → Postgres | Each statement is an independent HTTP request that can fail independently; no interactive transaction exists to bind them |
