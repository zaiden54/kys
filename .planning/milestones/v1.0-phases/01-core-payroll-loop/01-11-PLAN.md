<objective>
Close the D-14 consent blocker: the one-way salary overwrite is currently authorized by a bare
client-controlled boolean. The client resubmits the form's live values rather than the snapshot that
produced the prompt, and the server performs no check that the row still holds the amount it
disclosed. An edit after the prompt, or a concurrent write from the user's other device, therefore
destroys a value the confirming user never saw — with no audit trail to recover it.

Purpose: make the shipped behavior match D-14's intent — a replacement overwrites only the exact
value that was shown and explicitly confirmed.
Output: a server-signed, time-limited confirmation claim; two conditional single-statement write
primitives; an action state machine that re-prompts instead of writing whenever reality has moved;
and a client that confirms the snapshot it was prompted about.
</objective>

## User-story outcome

**As a** user correcting a salary I recorded earlier, **I want to** see exactly which stored value my
change will destroy and confirm that specific value, **so that** a stale prompt, a slip of the form, or
a change I made on my phone a minute ago can never quietly erase a number I was never shown.

## Design decision: bind consent to a server claim, then to the client snapshot, then prove the race

Task 1 is the tracer: it carries one confirmation round trip end to end — the server observes a row,
mints a signed claim describing it, the user confirms, and a single conditional statement writes only
if that exact row value survives. Task 2 makes the browser half honest by confirming the stored
snapshot instead of live form values and by disclosing both the destroyed and the replacing amount.
Task 3 proves the property that matters against the real database: a stale expectation cannot win.

**Reversibility note on D-14 itself.** 01-CONTEXT.md rates D-14 (overwrite with no audit trail) as a
**one-way** decision. That door was already chosen by the developer during discuss-phase and shipped in
plans 01-04 and 01-07, so per the reversibility guidance on decisions already made, no
`checkpoint:decision` is inserted to re-ask it; the rating is recorded here for the record. This plan
does not revisit whether to keep an audit trail — it makes the existing one-way write require
disclosed, bound consent.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form → Server Action | The amount, the effective date and the confirmation claim are all attacker-controlled FormData; only the claim's signature makes any of it trustworthy as a statement about what the server previously disclosed. |
| Server Action → confirmation claim verification | The claim is the only carrier of "what the user was shown"; forgery, replay past the time-to-live, or reuse across accounts must each fail closed. |
| Server Action → repository conditional write | The compare-and-swap is the last line of defence: it is what makes a concurrent write from the user's other device lose visibly rather than silently. |
| Device A session ↔ Device B session (same account) | Two authenticated sessions write the same dated row; the database is the sole arbiter. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

## Assumption-delta decision

The detector fired on "second device" (pluralization signal). **Decision: add alongside, no identity
promotion.** The identity model stays one authenticated user id owning one set of rows; this plan
treats a second device as a second concurrent *writer* against the same rows, handled by database
arbitration and a re-prompt, not as a new identity, tenancy, or per-device state dimension. No device
registry, device id, or per-device row is introduced. This is advisory and does not gate the phase.

## Flagged assumptions

- **Claim secrecy is not required, integrity is.** The claim is signed, not encrypted, and carries only
  facts the same user already sees in the prompt. Its job is to let the server vouch for what it
  disclosed, not to hide anything.
- **Ten-minute time-to-live.** Chosen so an abandoned prompt cannot authorize a write much later. An
  expired claim is not an error: the user is simply re-prompted against the current value.
- **Known-open WARNING, deliberately not planned here.** 01-REVIEW.md WR-01 (schedule and YTD Server
  Action rejections still surface as unhandled event-handler rejections) and WR-02 (login and
