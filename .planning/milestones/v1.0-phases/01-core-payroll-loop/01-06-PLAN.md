## Design decision: why a hand-rolled UTC+3 offset

Russia abolished seasonal clock changes in 2014 — Europe/Moscow is a fixed UTC+3 with no
DST. A fixed-offset helper is therefore exactly as correct as a tz-database lookup for
this timezone, and avoids adding `date-fns-tz` as a new dependency (which would trigger a
package-legitimacy human-verify checkpoint per this repo's documented executor deviation
rules, for zero correctness gain). 01-VERIFICATION.md's own `missing:` field names this
as an acceptable remediation.

## Design decision: which accessor family the helper must satisfy

**This is the single most important detail in this plan and it corrects 01-PATTERNS.md.**

01-PATTERNS.md sketches `nowInMoscow()` as an epoch shift whose *UTC* accessors read the
Moscow wall clock. That is only equivalent to Moscow wall-clock time when the host process
runs in UTC. But every consumer in this codebase reads **local** accessors:

- `nextPaymentOnOrAfter` (`src/domain/schedule/resolve-payment-date.ts:112-118`) calls
  `today.getFullYear()`, `today.getMonth()`, and `startOfDay(today)` — all local.
- `resolvePaymentDate` builds dates with the local `new Date(year, monthIndex, day)` form.
- `format(date, "yyyy-MM-dd")` from date-fns formats local fields.

So handing a UTC-shifted Date to that pipeline is correct only on a UTC server and is
*wrong by an extra offset* on any other host — including a developer machine set to MSK,
which would read UTC+6. The helper must therefore return a Date whose **local** fields
carry the Moscow wall clock, and must derive those fields without depending on the host
timezone. Both requirements are satisfied by: shift the epoch by +3h, read the shifted
instant's `getUTC*` fields, then re-materialise those fields through the local
`new Date(y, m, d, h, mi, s, ms)` constructor.

Known, bounded caveat to document in the module: the returned Date is a **wall-clock
carrier, not a true instant** — its epoch value is deliberately not the real current time.
Every consumer in this app is date-granular, so calendar-date fidelity holds in any host
timezone; only sub-day fields could shift if the host timezone happens to be inside its
own DST-gap hour at that wall-clock time. Never write this value to a timestamp column.
