  <name>Task 1: Decide how the monthly gross oklad splits across the avans and salary payments</name>
  <decision>When a user enters one monthly gross salary and two payment days, how much gross does each of the two payments carry?</decision>
  <context>
    This is a missing-information flag, not a scope reduction. SAL-01 says the user enters an "оклад «грязными»" — one monthly figure — and configures two payment dates per month. TAX-02 requires each payment to be taxed independently against the cumulative base at its own date, which means each payment needs its own gross amount. Nothing in REQUIREMENTS.md, ROADMAP.md, CONTEXT.md (D-01 through D-15), or 01-RESEARCH.md states how the monthly figure divides between the avans payment and the salary payment.

    The choice is visible in every number on the home screen, so it cannot be assumed silently. It is reversible — the split rule lives in one function in `forecast.ts` — but option B additionally requires a schema column and a database push, so it is worth deciding before the forecast is written rather than after.
  </context>
  <options>
    <option id="half-split">
      <name>Even 50/50 split of the monthly oklad</name>
      <pros>No schema change, no extra form field, no extra input burden at onboarding. Each payment carries half the monthly gross, both are taxed independently at their own dates, and the annual total is exactly the oklad times twelve. Matches the simplest reading of "оклад + two payment dates".</pros>
      <cons>Real employers commonly pay an avans of 40-50% computed from days worked in the first half of the month, so an individual payment can differ from the forecast by a few thousand rubles even though the annual total is right.</cons>
    </option>
    <option id="configurable-percent">
      <name>User-configurable avans percentage</name>
      <pros>Matches whatever the user's employer actually does, so each individual payment forecast is accurate rather than only the annual total.</pros>
      <cons>Requires adding an `avans_percent` column to `payment_schedule`, a second drizzle-kit push, an extra field in the schedule form, and validation. It also asks the user for a number many people would have to work out from a payslip.</cons>
    </option>
  </options>
  <resume-signal>Select: half-split or configurable-percent</resume-signal>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session cookie → server render | The identity used to select whose salary is read |
| repository → forecast orchestration → rendered HTML | Financial figures leave the server as display strings |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-02 | Tampering | Tax computation site | high | mitigate | `calculateNdfl` is invoked only inside the `server-only` forecast module during a server render; the home page and the card are asserted to contain no reference to `calculateNdfl` or `taxOnCumulative`, so no tax figure can be produced or altered in the browser and none is accepted back |
| T-01-01 | Elevation of Privilege | `src/app/(app)/page.tsx` | high | mitigate | The page derives its user id from `requireUserId()` and passes it to the forecast; the forecast passes it to ownership-scoped repository functions. | T-01-10 | Tampering | Tax-year selection for a payment date | high | mitigate | The tax year is taken from the resolved payment date and `UnsupportedTaxYearError` is asserted not to be caught, so an unverified year surfaces as a visible failure rather than a plausible number |
| T-01-04 | Information Disclosure | Salary and tax figures in logs | medium | mitigate | The forecast module contains no logging call (asserted by grep); figures reach only the rendered response for the authenticated owner |
| T-01-16 | Information Disclosure | Response caching of a per-user server render | medium | mitigate | The home route reads the session cookie through `headers()`, which opts the render out of static generation; the not-configured and configured branches are both produced per request rather than from a shared cached payload |
</threat_model>
