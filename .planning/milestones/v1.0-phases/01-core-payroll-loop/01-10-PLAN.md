## User-story outcome

**As a** salaried user who started using НаРуки partway through the year, **I want to** see my next
payment taxed against everything I have actually been paid since my year-to-date starting point,
**so that** the amount on my home screen matches what will really land in my account instead of
under-taxing me until my employer's own cumulative calculation catches up.

## Design decision: one vertical slice, then calendar hardening, then the persisted boundary

Task 1 is the tracer. It carries one real user path end to end — persisted schedule, salary history
and baseline, through a new pure accrual engine, into the repository, into `forecastNextPayment`,
into an asserted take-home number — and proves the number moves for a bracket-crossing scenario.
Task 2 expands that proven slice across the calendar situations real users are in: a raise mid-window,
the New Year reset, a payday that clamps or shifts onto another payday. Task 3 closes the persisted
boundary so the as-of date a user confirms in the form is exactly the boundary the engine accrues
from, and asserts the database-backed path against the same rules.

There is no schema, package, or route foundation to build; every task refines an already-shipped
vertical slice.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form → Server Action (`saveYtdBaselineAction`) | The as-of date and amount are attacker-controlled FormData; they define the accrual window's opening boundary and therefore the tax base. |
| Server Action / server render → repository | Cumulative income is derived per request from user-scoped rows; an ownership predicate omitted on any of the three reads leaks another user's income into a tax base. |
| Repository → pure accrual engine | The engine receives already-authorized rows; it must stay free of I/O and clock reads so its output is a pure function of the authorized inputs. |
| Server render → browser (`NextPaymentCard`) | Only the resolved date, gross, tax and net cross back; no baseline, no history and no error detail. |

## Flagged assumptions

- **Modelled, not observed, income.** Accrual assumes every scheduled payment between the baseline
  date and the forecast date actually occurred at the scheduled gross. The app holds no record of
  payments actually received, and PROJECT.md excludes payslip reconciliation from scope, so this is
  the only derivation available. A user who was unpaid for a period will see an over-taxed forecast
  until they correct their YTD baseline, which D-10 already permits at any time.
- **Baseline inclusivity.** The stored as-of date is treated as inclusive: the baseline covers
  everything up to and including that date, and accrual starts strictly after it. Task 3 makes the
  form's default agree with that reading; a baseline stored before this plan with a start-of-year
  as-of date and a mid-year amount will now be added to, not replaced by, accrual.
- **Known-open WARNING, deliberately not planned here.** 01-REVIEW.md WR-01 (schedule and YTD
  Server Action rejections still surface as unhandled event-handler rejections) is not in
  01-VERIFICATION.md's `gaps` block and is therefore out of scope for this gap-closure round. It is
  recorded here so it is not silently lost.
- **Assumption-delta checkpoint.** The detector fired on "second device" (pluralization) and
  "optionally" (optional). Decision: **no change** to the identity model. Cumulative income stays
  keyed on a single authenticated user id, the optional YTD answer is already modelled as an
  always-present baseline row carrying an `isEstimated` flag rather than as an absent value, and this
  plan introduces no second identity, tenancy or device dimension.
