<objective>
A user can add a one-off bonus or compensation tied to any date they pick — including a date with no
scheduled avans/salary payment — and see it taxed through the exact same cumulative НДФЛ engine as
regular salary, correctly changing the take-home amount shown on the home screen for that payment
(BON-01, BON-02). If the bonus is the soonest upcoming payment event of any kind, it becomes the
unified "next payment" the home screen shows (D-B10), with a base/bonus breakdown when it lands on
the same date as a scheduled payment (D-B09).

Purpose: this is the tracer slice for Phase 2. It proves the two riskiest architectural pieces before
any expansion work: (1) bonus income folds into `getCumulativeIncomeBeforeDate`'s single cumulative
chain without a parallel calculation path, and (2) `forecastNextPayment`'s next-event resolution
generalizes from "schedule only" to "schedule or bonus, soonest wins" without breaking any of
Phase 1's five existing forecast tests. Editing and deleting a bonus (D-B04, D-B06) and the full
history-list UI (D-B05's edit/delete affordances) are expansion work in Plan 02-02.

Output: a `bonuses` table live in Neon; a bonus repository (create + list); a bonus Zod schema; a
create-only `saveBonusAction`; `forecastNextPayment` generalized to resolve bonus-only and combined
next-payment events; `NextPaymentCard` rendering the base/bonus breakdown; and a `/bonuses` route with
a create form and a read-only history list.
</objective>

## Flagged assumptions

- **UI-SPEC's Form "long-text" consideration (note field with unusually long text) is not implemented
  as a custom truncation/tooltip widget on the input itself.** UI-SPEC describes the note *input*
  truncating with an ellipsis while typing, with the full text visible on focus. A native
  `<input type="text">` already scrolls horizontally to keep the cursor visible and never visually
  truncates its own live value with an ellipsis — adding custom JS truncation to a field the user is
  actively typing into would fight the browser's own editing affordances for no benefit. This plan
  resolves the consideration as: the input's native scroll behavior satisfies "stays editable/visible
  while typing," and the DISPLAY-side truncation UI-SPEC also asks for (ellipsis + hover tooltip in the
  list row) is implemented for real in Plan 02-02's `bonus-row.tsx`, where a note is read-only text
  rather than a live edit target.

## Design decisions made in this plan (not pre-resolved by CONTEXT.md)

- **Multiple rows per (user, date), no unique index.** 02-RESEARCH.md's Pattern 1 flagged this as
  `[ASSUMED — confirm during planning]` and tentatively recommended one merged row per date. This plan
  decides the opposite: each bonus is its own row with its own uuid, amount, date, and note. Rationale:
  D-B04 says amount *and/or date* can be edited on an existing bonus, D-B05 requires a full individual
  history, and D-B08 gives each bonus its own note — a merged-row design would make edit/delete
  ambiguous (which of two merged bonuses did the user mean?) and would destroy per-bonus notes on
  merge. Summation for tax purposes (D-B03) happens at query time in
  `getCumulativeIncomeBeforeDate`/`forecastNextPayment`, not at storage time.
- **Bonus dates are used literally — no D-02/D-03 weekend/holiday shifting.** 02-RESEARCH.md's Pitfall 2
  flagged this as an open question and tentatively leaned toward shifting. This plan decides bonus
  dates are NOT resolved through `resolvePaymentDate`. Rationale: `paymentSchedule.avansDay`/`salaryDay`
  are abstract day-of-month integers that must be resolved into a real calendar date every month —
  that is what `resolvePaymentDate` exists for. A bonus's `date` column is already a concrete calendar
  date the user picked in a date input; there is no abstraction step to resolve. If a user wants a
  bonus to land on a real business day, they pick that day directly in the date picker.
- **Bonus income is summed directly in `getCumulativeIncomeBeforeDate`, not folded through
  `accruedGrossBetween`.** 02-RESEARCH.md's Pattern 3 "Approach A" recommended extending
  `accruedGrossBetween` with an optional bonus-events parameter. This plan uses "Approach B" instead:
  `payment-accrual.ts` is left completely unchanged. Rationale: `accruedGrossBetween`'s six numbered
  rules exist entirely to handle day-of-month calendar resolution (D-02/D-03) that bonus dates do not
  need — threading bonus events through that machinery would mean giving them a fake resolution step.
  The single cumulative figure is still composed in exactly one place (`getCumulativeIncomeBeforeDate`),
  so this is not the "parallel cumulative calculation" anti-pattern RESEARCH.md warns against — it is
  the same one composition point, extended by one additional term.
- **No Phase-1-style confirmation-token flow for bonus edits.** Phase 1's D-14 salary replace flow needs
  a signed confirmation claim because a salary's natural key (`userId`, `effectiveFrom`) can collide.
  A bonus has no natural-key collision: it is identified by its own immutable uuid `id`, so an edit is
  always an unambiguous single-row `UPDATE ... WHERE id = $1 AND user_id = $2`. Plan 02-02 builds this
  without a confirmation dialog, consistent with D-B04's "can be fully edited at any time" wording.
