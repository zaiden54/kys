<objective>
Apply the Drizzle schema to the per-deployment Neon preview branch during Vercel preview builds, only when VERCEL_ENV=preview. Production builds, GitHub Actions CI builds, and local builds must stay unaffected.

Purpose: The Neon-Managed Vercel integration forks a data-bearing `preview/<git-branch>` Neon branch from `production` for each preview deployment and injects DATABASE_URL at build time, but the project has no migration files (schema is applied via `drizzle-kit push`). Without this step a preview deployment can run against a branch whose schema lags the code under review. Neon docs recommend running schema migrations in the Vercel build command.

Output: `scripts/apply-preview-schema.mjs`, an updated `build` script in `package.json`, and a short README note.
</objective>

  <files>scripts/apply-preview-schema.mjs, package.json</files>
  <action>
Create scripts/apply-preview-schema.mjs as an ES module executable with a `#!/usr/bin/env node` shebang. Match the header-comment style of scripts/verify-auth-security.mjs, but use a short block comment explaining: (a) it runs as the first half of the `build` script on every build, (b) it is a deliberate no-op unless VERCEL_ENV is exactly "preview", (c) why: the Neon-Managed Vercel integration forks a `preview/<git-branch>` Neon branch from `production` and injects DATABASE_URL into the preview build, and this project has no migration files so the schema is applied with `drizzle-kit push`, (d) production schema is intentionally NOT touched here and is still applied manually with `npm run db:push`, (e) GitHub Actions CI and local builds have no VERCEL_ENV so they skip.

Behavior, in order:
1. If `process.env.VERCEL_ENV` is not strictly equal to the string "preview", print exactly one line to stdout that contains the word "skipping" (lowercase) and the observed VERCEL_ENV value or "unset" (e.g. "apply-preview-schema: VERCEL_ENV is unset, skipping schema push"), then exit with code 0 (return from main; do not call process.exit(1)). VERCEL_ENV is not a secret, so echoing it is fine.
2. Otherwise read `process.env.DATABASE_URL`. If it is missing or empty, print an error to stderr that names only the variable (e.g. "FAIL [apply-preview-schema]: DATABASE_URL is required on Vercel preview builds, but the preview branch database URL was not injected") and exit with code 1. This must fail the build: a preview deployment without its branch DB must never deploy silently.
3. Otherwise run `npx drizzle-kit push --force` via `execFileSync` from node:child_process with the argument array form (`["drizzle-kit", "push", "--force"]`), `stdio: "inherit"`, and `env: process.env` passthrough (DATABASE_URL is already present in the environment; drizzle.config.ts reads process.env.DATABASE_URL). This mirrors the idiom already used in e2e/ci-branch-setup.mjs. `--force` is required so drizzle-kit never blocks on an interactive data-loss confirmation in the non-TTY Vercel build. Only the preview branch (a copy-on-write fork) can be affected.
4. Wrap the whole flow in a `main().catch(...)` handler like e2e/ci-branch-setup.mjs: on any thrown error (including a non-zero exit from drizzle-kit, which execFileSync surfaces as a thrown error) print one generic message to stderr such as "FAIL [apply-preview-schema]: drizzle-kit push failed" plus the error's `.message` only if it cannot contain secrets (execFileSync's message is just "Command failed: npx drizzle-kit push --force"; do NOT print the error object's env, stdout/stderr buffers, or options), then `process.exit(1)`.

Hard rules (per threat model): never log, interpolate, or concatenate the DATABASE_URL value into any string, message, or error; reference the variable by name only. Do not add any new dependency (drizzle-kit is already a devDependency and Vercel installs devDependencies for the build). Do not read or write .env files. The missing-URL failure must be a hard exit 1, never a warning. `npx` with execFileSync is intentionally POSIX-oriented, same as e2e/ci-branch-setup.mjs: the push path only ever executes on Vercel's Linux builders, while the skip path is what runs locally and in CI.

Then edit package.json: change only the `build` script from "next build --webpack" to "node scripts/apply-preview-schema.mjs && next build --webpack". The `&&` is load-bearing: a failed push (exit 1) must abort the build so a broken preview never deploys. Do not touch `db:push`, `dev`, or any other script, and do not add a postbuild/prebuild hook.
