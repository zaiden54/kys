<objective>
Speed up in-app navigation. Today clicking a nav item (for example "Главная") shows no feedback for 1-2 s and then the page swaps in.

Purpose: remove the four verified causes (treated as facts, already checked by the orchestrator):
- RC-1 Region mismatch: Vercel functions run in iad1 while Neon is in aws-eu-central-1 (Frankfurt); each neon-http query crosses the Atlantic and the home page does ~5-6 sequential round trips. Fix: vercel.json with regions ["fra1"].
- RC-2 Layout blocks navigation: per this Next 16.3 version's docs (layout.md "Interaction with loading.js", loading.md), a layout that reads headers()/cookies() makes navigation block until the layout renders and no loading.js fallback is shown. Fix: take the session check out of the (app) layout, replace it with an optimistic src/proxy.ts redirect (Next 16 renamed middleware to proxy), keep the authoritative check in pages/actions, and add loading.tsx files so a skeleton is prefetched and shown instantly.
- RC-3 Session read twice per request (layout + page) and on every Server Action. Fix: React cache() around getSessionUser, plus Better Auth cookieCache (5 min).
- RC-4 Duplicate data loads: forecastNextPayment and computeAnnualSummary each load the same five tables on one home render. Fix: request-scoped React cache() on the five READ repository functions.

Output: src/proxy.ts (+ unit test), slimmed (app)/layout.tsx, page-level guards on bonuses/vacations pages, cached session + repository reads, cookieCache config, vercel.json, and four loading.tsx files.

Planner findings that refine the brief (all stay inside its intent):
1. src/app/(app)/bonuses/page.tsx and src/app/(app)/vacations/page.tsx call requireUserId() only inside their Suspense child components, not at page level (home, onboarding and settings/salary pages do call it at page level). Task 1 adds a page-level guard to both; after Task 2 the duplicate call is free because getSessionUser is memoized.
2. e2e/auth.spec.ts asserts page.waitForURL("/login") and pathname === "/login", so the proxy must redirect to plain /login with no ?next= parameter.
3. Verified safe to memoize: every consumer of the five read results only .map/.filter/.reduce them or sorts derived copies (checked forecast.ts, annual-summary.ts, salary-repository.ts computeCumulativeIncome, calculate-average-daily-earnings.ts); nothing mutates a raw returned array in place. No Server Action calls these reads before a write (writes use insertSalaryIfAbsent / replaceSalaryIfUnchanged / checkOverlapVacations / deleteBonusIfFuture, none of which are memoized). Under vitest, react's default build is used where cache() is a pass-through, so existing unit/integration tests are unaffected.
4. Known limit of the cookie cache (not a defect, no scope change): the app does not use Better Auth's nextCookies plugin, so a session lookup made from a Server Component cannot re-issue the refreshed cache cookie. The cache is therefore most effective in the 5 minutes after sign-in; afterwards a lookup falls back to the database (still deduplicated per request by cache()). Correctness is unaffected. Do not add plugins in this task.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> proxy.ts | Untrusted Cookie header; presence check only, never proof of identity |
| browser -> page / Server Action | Authoritative boundary: requireUserId() validates the session with Better Auth |
| signed session cookie cache -> getSession | Better Auth trusts its own signed cache cookie for up to 5 minutes without a DB read |
| request -> React cache() | Memoization scope is one server request; keyed by the server-derived userId |
